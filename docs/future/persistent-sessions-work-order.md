# persistent sessions — work order

two stages. stage 1 is backend-only and verifiable headless with curl; stage 2 rewires the frontend around the mirror model — state is the working truth, the store is its durable mirror — and synthesizes `docs/current/`. the spec is `persistent-sessions.md` in this directory; its seam census carries the settled calls, including the 2026-08-19 mirror-model ruling that retired the store-as-source-of-truth machinery (operations queue, coalescing, transition tokens, per-class failure ledger). `/api/chat`, the SSE protocol, and `internal/llm` are untouched.

## stage 1 — backend store + api

### config — `internal/config/config.go`

- `DataDir string` — optional; the location of the session store.
- `func (c *Config) SessionDataDir() (string, error)` — returns the resolved data directory: `DataDir` when set (a leading `~` expanded to the user's home directory via `os.UserHomeDir`, so the documented example works as written), else `$XDG_DATA_HOME/pane` when `XDG_DATA_HOME` is non-empty, else `~/.local/share/pane`. mirrors the XDG handling in `globalConfigPath`.
- `pane.yaml.example` and the `pane new` template gain a commented line near the listen block: `#data_dir: ~/.local/share/pane` (comment: location of the session store; default shown).

### store — `internal/session/store.go`

`type Store struct { dir string; mu sync.Mutex }` where `dir` is the sessions directory.

- `NewStore(dir string) (*Store, error)` — `os.MkdirAll(dir, 0o700)`, then a write probe: create a temporary file in `dir` via `os.CreateTemp`, close it, and remove it; if any step fails, `NewStore` returns the error. the probe is required because `MkdirAll` alone succeeds on an already-existing directory even when the process cannot create or replace files in it — a store that starts clean and then fails on its first save would break the settled fail-fast behavior. called once at startup; a failure here is fatal (see main).
- `safeID(id string) (string, error)` — rejects empty, `.` and `..`, anything containing a path separator, and anything where `filepath.Clean(id) != id`. the final guard: `filepath.Join(dir, id)` must have `dir` as its cleaned parent. this is defense against a URL segment the mux already keeps slash-free; the store does not trust it.
- `List() ([]Summary, error)` — reads every `*.json` in `dir`. `Summary` is a small struct whose `ID` is the file's name stem, with `Title string; CreatedAt, UpdatedAt int64` filled by a forgiving `dd` bind of the body's projection fields under explicit camelCase name tags (`createdAt`, `updatedAt`) — the project's JSON convention, exact-key in both directions, so a differently-cased body projects the fields it actually holds rather than being case-folded into the canonical shape. files that fail to read, whose body is not a JSON object, or whose name stem fails `safeID` are skipped with `dl.Warnf` — the last clause guarantees the rail lists only ids the item endpoints can address (a `*.json` file whose stem the rule rejects, e.g. one literally named `.json`, could not be fetched from any `GET`, so publishing it would be a ghost entry) — and the id needs no check against the body, because the id is the name. sorted by `UpdatedAt` descending, `ID` ascending as the tiebreak.
- `Get(id string) ([]byte, error)` — `safeID`, then read. returns the stored bytes only if they are a JSON object (valid JSON whose first non-whitespace byte is `{`); otherwise an error naming the id.
- `Save(id string, doc []byte) error` — `safeID`; reject bodies over 32 MiB; validate the document with the project's `dd` JSON binding in strict mode: strict intake rejects a non-object top level, duplicate keys, trailing data, and type coercion, and a well-formed JSON object is a valid document — the id is the path's key (checked by `safeID`), not a field of the body, so there is nothing to compare and no read-time validation to run; the body binds to a shape with no declared fields (a `map[string]any` tagged `+extra` as the declared home for everything the store does not interpret), so the check is exactly "is this a well-formed JSON object". then write atomically: temp file in `dir` (`os.CreateTemp`, a name the `List` glob ignores), write, rename over the target — `os.CreateTemp` creates the temp file at `0600` and the rename preserves that mode, so a document is owner-readable from the first byte it holds and never passes through a world-readable state; with `defer os.Remove(tempPath)` registered immediately after the successful create, every failure path between create and rename (write, close, rename) takes the fragment with it: after a successful rename the remove is a no-op on a name that no longer exists, but a live store whose disk fills up or directory goes read-only under it does not accumulate one debris file per failed save. the orphaned-temp-file residual that remains is the crash case only — a temp file a dead process left behind, which no in-process cleanup could ever remove (see the spec's accepted residuals). the mutex serializes every file operation — `Save` is a single write with no read phase; the rename is what keeps a file name whole for `List` (which reads only `*.json`), and the mutex is what serializes the file operations so that a `List` or `Delete` never observes an intermediate state.
- `Delete(id string) (bool, error)` — `safeID`, remove; reports `false` when the file was absent, no error for it.
- typed errors — the store returns distinct sentinel errors for the failure classes the api maps to client errors: `ErrUnsafeID` (path containment failed), `ErrInvalidDocument` (the body is not a well-formed JSON object, or fails strict intake), and `ErrOversized` (body over the 32 MiB cap). operational filesystem failures — temp file, write, rename, permission — are returned as wrapped stdlib errors and are deliberately none of the sentinels. this is what lets the handlers separate "the client sent something bad" (4xx) from "the disk failed" (5xx).
- all file operations under `mu`.

### api — `internal/api/sessions.go` + `api.go`

- `API` struct gains `sessions *session.Store`. `NewAPI` takes it.
- routes: `GET /api/sessions`, `GET /api/sessions/{id}`, `PUT /api/sessions/{id}`, `DELETE /api/sessions/{id}` — there is no collection route: clear-all was removed from the design (round-4 review triage, 2026-08-19), and bulk deletion of the estate is the operator's file operation on the data directory.
- `handleListSessions` — `store.List()`, the projection fills `Summary` — `ID` from the file's name stem, the rest with a forgiving `dd` bind under explicit camelCase name tags (`createdAt`, `updatedAt`) — exact-key in both directions, the project's convention — and responds `{"sessions": [...]}` through `dd.UnbindJSONWriter`. an empty store returns `{"sessions": []}`, never null.
- `handleGetSession` — missing: `404 {"error": "session 'id' not found"}`. stored but unparseable: `500 {"error": "session 'id' is not a valid document"}`. otherwise the raw stored bytes with `Content-Type: application/json`.
- `handleSaveSession` — `io.ReadAll` the body; `store.Save`; `ErrUnsafeID` / `ErrInvalidDocument` → `400 {"error": "..."}` with the store's reason, `ErrOversized` → `413`, and any other store error (an operational filesystem failure) → `500 {"error": "..."}` naming the failure — a disk write error is never reported as a client error. success `204`.
- `handleDeleteSession` — absent: `404`; otherwise remove, `204`.
- `/api/config` is unchanged.

### main — `cmd/pane/main.go`

after config load, before the server starts:

```go
dir, err := cfg.SessionDataDir()
// on err: dl.Fatalf("session store: %v", err)
storeDir := filepath.Join(dir, "sessions")
store, err := session.NewStore(storeDir)
// on err: dl.Fatalf("session store: %v", err)
dl.Infof("session store: '%s'", storeDir)
```

`api.NewAPI` receives the store.

### stage 1 verification

- `make test` (go test + vet) green.
- headless pass with a temp config: `data_dir: <tmp>`, a dummy endpoint, `listen: 127.0.0.1:18400`.
  - `GET /api/sessions` → `{"sessions": []}`.
  - `PUT /api/sessions/abc` with a conversation document body → 204; `GET /api/sessions/abc` returns the bytes unchanged (the body carries no id — it is the file's name); the list shows its projection sorted by updated, id ordinal-ascending as the tiebreak.
  - `PUT` with a body that is not a JSON object (an array, a bare string) → 400; with duplicate keys or trailing data → 400 (strict intake); with invalid JSON → 400; path via `GET /api/sessions/..` → not a route (mux), and a directly-constructed store call with `..` fails `safeID`. a file renamed out of band (`mv abc.json zed.json`) is listed and served as `zed` — the id is the name, so nothing fails. a file renamed out of band to a URL-reserved name (`mv abc.json 'issue#1.json'`) is listed as `issue#1` and round-trips `GET` / `PUT` / `DELETE` under its encoded form (`/api/sessions/issue%231`) — the encode lives in the frontend adapter (and in curl here), the backend is unchanged.
  - a forced operational store failure (e.g. a read-only data directory) on `PUT` → 500 naming the filesystem error, never 400/413.
  - `DELETE /api/sessions/abc` → 204; again → 404; a collection `DELETE /api/sessions` (the retired clear-all route) is not a route — the mux answers `405` (the path is known to the list route, the method is not), and bulk deletion remains the operator's file operation.
  - two `PUT`s of different sizes to the same id: the file is always a complete document (atomic rename).
- a non-writable `data_dir` fails startup with the clear error — through the `NewStore` write probe, which catches the case where the sessions directory already exists but the process cannot write inside it.
- `data_dir: ~/pane-test` creates its tree under the home directory, not a literal `./~` beneath pane's working directory.

## stage 2 — frontend rewiring + docs

### types + config

- `types.ts` gains `SessionSummary { id: string; title: string; createdAt: number; updatedAt: number }` (its `id` is the filename the store reports). `Conversation` drops `id` — the id is the store's key (the file's name; `activeId` in the app), not a field of the document. the in-memory and on-disk shapes are identical, so the round trip is byte-transparent: no stripping on save, no injection on get.
- a failed `/api/config` fetch is storage-independent — the store works regardless — but its consequences (an empty model list, a send without an explicit model failing) would otherwise be unexplained. the operator must not have to infer it: `useConfig` exposes the fetch failure as a state field instead of catching it into `emptyConfig`, and the app renders it through the arc's existing quiet error line once loading has ended — the line names the failure and points at the recovery (restart pane, reload), and it persists until reload since the binary it accuses sits behind the page. no retry: the client would be hammering a fetch its own binary just failed to serve. a dead or late config is a visible state in this app, not a silent one.

### adapters — `ui/src/lib/sessionStore.ts`

the interface from the spec. one implementation:

- `diskSessionStore` — `list` fetches `GET /api/sessions`; `get(id)` fetches the document body and parses it as a `Conversation` — the id the caller asked for is the document's id, so there is nothing to inject; `save(id, doc)` PUTs `doc`'s bytes to `/api/sessions/<id>` — nothing to strip; `remove` DELETEs the id. every item URL is built as `/api/sessions/` + `encodeURIComponent(id)` — a safe filename is not necessarily a URL-safe string: `issue#1` is a legal conversation name, and the `#` in a URL built by string concatenation would truncate the request at the fragment separator, sending a different path and 404-ing the conversation into a ghost; the mux hands the handler the decoded segment, so `issue%231` arrives as `issue#1` and the store's id rule passes it unchanged. every response is checked against its documented status: `200` for list, `200` for get with `404` as the one case that resolves to `null`, `204` for the mutations. any other status rejects with the backend's message, decoded by one small helper that reads both documented error shapes — a plain `error` string (the shape the handlers above emit: `{"error": "session 'abc' is not a valid document"}`) and the nested `error.message` object (retained for robustness) — falling back to the HTTP status text only when the body is unparseable or carries neither. a rejection from any operation, reads included, carries a message the error line can show, so a save rejected over the 32 MiB cap surfaces the backend's reason rather than a bare status text; a network failure rejects the same way. there is no warn-and-swallow path: a save that does not reach disk is a failure the UI shows, never a success the app acts on.

### hook — `ui/src/hooks/useSessions.ts`

`useSessions()` — the mirror hook, shaped like `useLocalStorage` so the app code around it keeps its form:

- binds to `diskSessionStore`. state: `copyRef` — a ref holding the working copy, the mirror's source of truth, hydrated on mount through the hook's internal non-mirroring path (it seeds the ref and the state together and issues no save, so a load never re-PUTs the estate) — and `conversations`, the React state that renders the same copy (renders read the state; the mirror reads the ref; the setter keeps the two equal), `loading` (true until the initial `list` succeeds and its documents are installed; a failed `list` leaves it true), `error` (one slot: the most recently failed operation's decoded message, cleared by the next successful store operation). exposes `{ conversations, setConversations, loading, error, remove }`.
- hydration on mount: `store.list()`, then a `get` for each listed id (parallel fetches — distinct ids, loopback); the resolved documents become the working copy **in the order the list returned them** (updated descending, id ordinal-ascending — the store's comparator), not in get-resolution order. `loading` stays true until the working copy is **fully installed** — the `list` **succeeded** and the `get` for every id it listed has settled — and the hook flips it false in the same step it installs the copy: one boundary, one meaning. the hydration effect keeps an effect-local cancellation flag set by its cleanup, and installing the working copy into the ref and the display state — and the `loading` flip — is skipped when the flag is set: the app mounts under React StrictMode, which repeats effect setup in development, and without the flag a superseded instance's late results could install a stale snapshot over a local change the surviving pipeline made; production mounts once, so the flag is a no-op there. a failed `list` settles **nothing**: `loading` stays true, the copy stays empty, the error line names the failure, and the session gate stays closed over the unknown estate — a mutation issued against an untrusted empty copy would run over an estate the tab never read, with a rail that misrepresents the store as empty — with the recovery a reload after the backend recovers (restart pane, reload; the same guidance the arc gives for every store failure). a `get` that fails for one id drops that entry, names it in the error line, and still settles the transition with the rest of the estate — one unreadable file never strands the estate and never holds the session gate open.
- `setConversations(updater)` — a ref-backed update function with the same call shape `useLocalStorage` returns: at call time the wrapper reads the previous copy from `copyRef`, derives the next copy by applying `updater` to it, installs the next copy into `copyRef` and the React state (state is the display projection), and enqueues the diff between the two copies onto the serial chain **before returning** — added or reference-changed conversations are `save`d (the app's immutable updates build new objects only where they changed; a reference-unchanged entry is not saved). the mirror runs exactly once per call, at call time: never inside React's updater (react may invoke updaters more than once — StrictMode, concurrent re-renders — so I/O there fires speculatively or twice) and never in a later effect (effects settle after the state they mirror has logically moved, so a diff computed there can join the chain after a logically earlier operation — a clear that repopulates the swept directory), and that is the failure mode this pinning exists to exclude. removals are not diffed — the destructive handler calls `remove(id)` explicitly, because it awaits the settle to release the guard. every store mutation joins one serial promise chain in invocation order — a handful of lines, the adapter's entire ordering machinery: a `remove` issued after a save cannot execute ahead of it and re-create the file, because the save was already on the chain the moment its `setConversations` call returned. the only reader is the initial hydration, and the app's session gate keeps every mutation behind it (no store mutation is issued while `loading` is true), so there is no read-ordering machinery, and there is no coalescing: each mirrored commit is one PUT, and a long turn shows one PUT per commit — the mirror's honest behavior on a loopback appliance where a disk write is cheap.
- a failed operation — a mirrored write, a `remove`, the hydration `list` — records its decoded message in `error` and nothing else: no per-class tracking, no sticky entries. the next successful store operation clears the slot. this is the visible form of the `console.warn` the app has always used for the localStorage mirror, and the accepted residual in the spec names what the simplification trades away (a later success on another conversation clears the line) and why it is safe here (the divergence self-heals on the next write of the affected conversation).

### App rewiring — `ui/src/App.tsx`

- `conversations` / `setConversations` (useLocalStorage) are replaced by `const { conversations, setConversations, loading, error: sessionsError, remove } = useSessions()`. everything else around `conversations` — the find, the sync effect, the commit effect, the handlers — keeps its shape: `setConversations` takes the same updater function in and returns nothing, the only difference being where the mirror happens — at call time against the hook's ref, not in a storage write behind the scenes.
- `activeConversation = conversations.find(c => c.id === activeId)` — as today, now over the hydrated working copy. there is no `activeDoc`, no transition token, no seeded-id set: selection is a find, and the sync effect — a layout effect (`useLayoutEffect`), keyed on `activeId` **and** the hook's `loading` flag — loads the found conversation into the chat hook via `chat.loadConversation(activeConversation)`, which seeds messages from the conversation's own array reference and the usage record from its record (an omitted key ≡ `null`) — the reference behavior is what the commit guard below relies on. it is a layout effect rather than a passive one on purpose: react runs it after the dom mutation but before paint, flushing the state it seeds synchronously, so no painted frame exists in which the gate is open while the chat's messages, usage record, and snapshot still hold the previous conversation's state (or, during the hydration window, the empty state) — a send pressed the instant the gate opens, at the hydration settle or right after a selection click, builds from the loaded history, and the meter wears the selected conversation's reading in the first painted frame. the effect is a no-op while `loading` is true — during hydration the rail is empty, the session gate is up, and no user action can change the selection, so the empty find of a retained `activeId` against the not-yet-installed copy is simply skipped, seeding no snapshot and stamping no owner. when `loading` flips false the effect runs its normal branch against the installed copy — the **hydration-completion transition**: a retained id that matches loads its document and seeds `savedSnapshot` from the document's own references, so the retained selection comes back with its full history on screen and a subsequent send builds from that history, never from the empty state of the hydration window; a retained id that matches nothing (the ghost case) sets `activeId` to null — the effect's null branch re-runs and resets the chat state, the owner, and the meter reading together (`loadConversation(null)` in place of the old `setMessages([])`), so the ghost id is never left as the commit owner and a send after the clear takes the create branch instead of streaming work that cannot be mirrored to any conversation. when nothing is found outside that transition, the same null branch runs for a deselection, dropping the just-deselected conversation's messages and meter reading. the one-shot `skipNextConversationSyncRef` stays exactly where it is: it exists so a send that creates a conversation is not clobbered by the sync effect's load of the empty document, and the mirror model does not change that.
- new state: `savedSnapshot` — a ref holding the (messages, usage) references the last mirrored document for the active conversation holds, usage normalized (an omitted key ≡ `null`). seeded from the loaded conversation's own references when the sync effect loads it — including at the hydration-completion transition, where the retained selection is reconciled against the installed copy — before `chat.loadConversation` runs — and advanced to the references just mirrored when a commit writes. the commit effect (keyed on `chat.messages`, `chat.usageRecord`) stays a passive `useEffect` — it writes, it does not paint, so a passively flushed run can never show the user another conversation's state — and keeps its existing clauses — the owner matches `activeId`, messages non-empty — and gains one: while chat's (messages, usage) are the same references `savedSnapshot` holds, it issues no write. this is the read-is-not-a-write guard: selecting or reloading a conversation emits no PUT, so the stored document's `updatedAt` and the rail's last-activity ordering are untouched by a mere selection, closing the latent re-write quirk the spec's shape section names. both sides normalize the optional `usage` field identically, so a document that omits the key reads as unchanged whether it arrived by hydration or by in-memory creation, and the guard holds for every document the conversation shape declares valid.
- new state: `destructivePending` — reactive boolean state, true only while a delete of the active conversation is in flight, plus a mirror ref updated by the same helper. the state is what closes the component-level gate: it drives `canSend`, so raising the guard re-renders `ChatView` with the send button and the retry button visibly disabled and the Enter path retaining the typed text — a ref alone would not re-render, and the buttons would stay enabled, and the Enter path could clear the input before the app-level guard refused the send. both handlers set state and mirror ref synchronously before issuing the operation, and clear both when it settles. the handlers' same-turn early-returns read the mirror ref, since state read inside the same event closure is stale by one render — while it is true, `canSend` is false and the new-conversation, send, selection, and further delete handlers early-return. the selection handler is among them for a sharper reason than the others: selecting during the window would re-attach commit ownership through the sync effect, reopening the fence — a message mutation on the selected conversation (even a thinking-collapse toggle) then commits a save behind the in-flight delete, which re-creates the file after the deletion with no error. a rail click dropped in the brief window is the price; the same click works once the window closes.
- the session gate: `canSend` = `!loading && !destructivePending` — on top of the composer's existing empty-input rule, the composer is gated on hydration settling and on the destructive-pending window; and the same flag disables the new-conversation controls (toolbar and rail), with `handleNewConversation` early-returning on it as a second line of defense. the gate is total because the hook's read-before-mutation assumption — the only reader is the initial hydration — depends on it: a new-conversation PUT issued before the hydration snapshot settles is overwritten by it (a file on disk the rail never shows), and a failed initial list holds the gate closed until a reload after recovery: the gate opens only over an estate the tab actually read. `loading` moves only true→false, so state suffices for the hydration half (no mirror ref), unlike the destructive guard, which moves both ways. and the flip instant is safe to open on, because the selection sync is a layout effect: the first painted frame after `loading` goes false already shows the active conversation's messages, meter reading, and snapshot, so the gate needs no second 'chat state is settled' condition.
- `handleSelectConversation` — unchanged: `chat.abort()`, `setActiveId(id)`. the sync effect does the rest, synchronously from state; no request is issued for a selection.
- `handleNewConversation` — a no-op while `loading` or `destructivePending` (the new controls are disabled in both windows) — otherwise as today: `chat.abort()`, build the empty document, `setConversations` (the mirror `save`s it), `setActiveId`. no seeded-id machinery — nothing fetches on selection, so there is nothing to bypass.
- `handleSend` — as today, gated by the component-level `canSend` plus a same-turn early-return on the mirror ref. the no-active-conversation branch keeps its `skipNextConversationSyncRef` one-shot. a send that reaches the wire before `/api/config` has landed names no model unless the reader set an explicit override, and it then fails visibly through the chat's existing error path — no new gate, the behavior today's app already has.
- `handleDeleteConversation` — state-first, as today: `setConversations(filter)` moves the conversation out of the working copy; the handler then calls `remove(id)` (joining the serial chain). when deleting the active one it first raises the `destructivePending` guard, aborts the in-flight turn, and detaches the commit owner, so nothing streams and mirrors behind the delete; the guard releases when the `remove` settles. on failure the selection is left in the post-delete state — the screen shows what state holds, the error line names the failure, and the disk still holds the conversation, so a reload restores it (the state-first mirror's failure mode, recorded in the spec's accepted residuals). deleting a non-active conversation is a plain state update plus `remove` with no guard — a different id cannot undo the operation.
- `onRetry` — `ChatView` receives `canSend` and gates its retry button on it, exactly as it gates the send button and the enter path: the retry is the one other path that starts a turn, and the gate keeps it from starting one that the detached owner would never mirror. the app passes `canSend ? chat.retryLastRequest : () => {}` — or equivalently `ChatView` checks the flag before invoking `onRetry`.
- the meter's input is derived: the toolbar receives `activeConversation ? chat.usageRecord : null` — during hydration (no working copy yet) and with no active conversation the meter reads `?`, and otherwise it always shows the active conversation's record, because the sync effect seeds it and `loadConversation(null)` resets it with the selection.
- the error line: while the app's derived error — `sessionsError` when non-null, otherwise the config error from `useConfig`'s exposed failure state — is non-null, the app renders one muted line near the conversation input (placement at the implementer's discretion within pane's aesthetic — no new chrome, no dismiss control). the slot holds the most recently failed store operation's message and clears on the next successful store operation; the config failure persists until reload since nothing on the page can clear it. the ordering is fixed — the session error when present, otherwise the config error — so a session failure takes the line over the persistent config failure, and the config failure resurfaces when the session failure settles; a dead backend, which fails both at load, shows the session failure until the reload that clears both.
- `ConversationList` receives the working copy's `conversations` (as today) and renders them in (updated descending, id ordinal-ascending) order — the same comparator the store's `List` applies: the id comparison is UTF-8 byte order on both sides, implemented on the frontend by comparing the id's `TextEncoder` bytes (a few-line helper; never the raw-string operator, which orders by UTF-16 code units, and never `localeCompare`), so screen order and disk order agree for any id the store accepts; its title fallback for empty titles stays where it is. a commit that stamps `updatedAt` moves the conversation to the top in the same render, through this display sort.
- `canExportActiveConversation` and export read from `activeConversation` + `chat.messages`, as today.

`useChat` is untouched: `loadConversation` already seeds `usageRecord` from the conversation object and seeds messages from the conversation's own array reference (verified against the current code) — the reference behavior is what the commit guard's identity comparison relies on.
