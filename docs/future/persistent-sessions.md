# persistent sessions — spec

the record of the work should outlive the tab. this arc moves conversation storage from the browser onto disk behind the backend. disk is the only mode: the record lives under a configurable data directory, one JSON file per conversation, and the browser keeps only per-browser view state.

## problem

the founding principle — stateless backend, conversations in the browser — fits the appliance story badly in one specific way: the record of the work does not outlive the tab. a browser profile wipe, a reimage, a switch of browsers, and every conversation is gone. markdown export saves what the reader thinks to save in the moment; the rest is lost.

the context meter made the asymmetry concrete (2026-08-17): the per-conversation usage record is self-contained on the conversation object, and the design session noted that when storage leaves the browser the record moves with the conversation — it serializes with the history it describes and needs no re-derivation. this arc is that revisit.

deferred item 6 in `docs/current/pane.md` (no graceful behavior when localStorage fills) is resolved by construction: the app writes only small per-browser view state to localStorage, and the conversation record — the data that actually fills a profile — lives on a disk store with no practical quota.

## shape

storage ownership moves to the backend, unconditionally. the browser cannot write to disk; only the backend can. the protocol does not move: `/api/chat` still receives the full history on every request, the backend keeps no in-memory conversation state, and the SSE stream is unchanged. what moves is where the record lives, not how it flows.

there is no mode to select and no config key that selects one: the store is always on, and its only setting is the location of the data directory. one deployment the move degrades is the ephemeral container: its default data directory dies with the container, so a container that wants the record to outlive itself points `data_dir` at a mounted volume.

the runtime shape is a **mirror**, not a sync protocol. the browser holds the full estate in the hook's working copy — a ref, and the React state that renders it — the same working-copy model the app has today on localStorage — and the store is its durable mirror: hydrated on load, persisted on every change. selection is a synchronous find over state, not a fetch; the app code around `conversations` keeps the exact shape it has today. the operator settled this model on 2026-08-19, trading live cross-tab sync for reload-scoped sync: a change made in one tab is on disk immediately, but another tab sees it only after a reload. with the store no longer the source of truth the app reads from, the machinery the earlier store-as-source-of-truth design needed — an operations queue, save coalescing, transition tokens, a per-class failure ledger — is retired with it: none of it buys anything the app did not already have on localStorage.

one visible refinement lands with the move: the conversation rail sorts by last activity (updated, descending) instead of insertion order. replying to an older conversation brings it to the top — standard chat-client behavior, and the ordering a persistent record wants, since the rail's job becomes "where was i". the ordering carries a guard with it: opening or reloading a conversation is not a write. the app snapshots the state it loads and commits only on a change to it, so a mere selection can never re-stamp a conversation's last activity. (in the shipped code a load does in fact re-write the record — a latent quirk, invisible under today's insertion order that last-activity ordering would otherwise make visible.)

### the store

`internal/session` is a new backend package: a file-backed document store.

- **one file per conversation.** `<data_dir>/sessions/<id>.json`, where the data directory resolves from `data_dir` in config, defaulting to `~/.local/share/pane` (XDG_DATA_HOME-aware, mirroring the existing config-path resolution). a leading `~` in the configured value expands to the user's home directory, so the documented example works as written. the `sessions/` subdirectory leaves room for future disk data in the same home.
- **opaque documents.** the file's name is the conversation's id; the file's body is the conversation's content in the camelCase shape the frontend already speaks (`title`, `messages`, `createdAt`, `updatedAt`, `usage`). the id is not a field of the body, so the stored bytes are exactly what the app holds, and there is no wire translation in either direction. the backend never interprets the content — it validates only that the body is a well-formed JSON object (strict intake: a non-object top level, duplicate keys, trailing data, or type coercion is rejected). because the body carries no id to police, a file that is renamed or hand-edited is simply a conversation under its new name, or the same conversation with new content — no read-time validation is needed, and the only thing that can make a file unloadable is a body that is no longer a JSON object, which gets the directed failure recorded in the residuals below.
- **projection for the list.** the rail needs the id — the file's name — plus `title`, `createdAt`, `updatedAt` from the body. the list reads that projection from each file, sorted by updated descending, with the id ordinal-ascending as the tiebreak — ordinal meaning UTF-8 byte order: Go compares ids as the UTF-8 bytes a string is, and the frontend compares the id's `TextEncoder` bytes against the other's (a few-line helper in the rail's sort), never the raw-string operator (JavaScript orders by UTF-16 code units, which diverges from Go on supplementary-plane characters) and never a locale-sensitive comparison — the same comparator on both sides, so screen order and disk order agree for every id the store accepts, including a rename to a name carrying emoji. a file whose name fails the same id rule the item endpoints apply, whose body is not a JSON object, or whose projection fields will not bind, is skipped with a logged warning — one bad file never breaks the rail, and the first clause keeps the rail to exactly the set of ids the item endpoints can address, so nothing the rail shows is unopenable. the projection is the filename plus the body's camelCase content fields: a subset of the opaque document and its name, one case per resource.
- **atomic writes.** temp file in the same directory, then rename. the directory is created at `0700` and the documents are written at `0600` — a store of prompts and tool results is owner-readable, and a `0700` directory keeps it that way even where the home directory is traversable by another local user. a per-store mutex serializes operations — one binary, one process, no locking protocol.
- **fail fast.** a store that cannot be created fails startup with a clear error. there is no fallback to degrade to: an appliance whose record cannot be written fails loudly at startup rather than serve an empty rail that pretends to remember.

### api

additions only. every existing endpoint is unchanged, and `/api/config` gains no field — the store has no setting to report.

| endpoint | method | description |
|---|---|---|
| `/api/sessions` | GET | list: projections of every stored conversation, sorted by updated descending, id ordinal-ascending as the tiebreak. `{"sessions": [{id, title, createdAt, updatedAt}]}` |
| `/api/sessions/{id}` | GET | the session document's body, as stored — the conversation's id is the URL's path |
| `/api/sessions/{id}` | PUT | upsert the document body under that id. create-or-replace; the frontend owns id generation, as it does today — the id rides in the path, not in the body |
| `/api/sessions/{id}` | DELETE | delete one conversation |

error behavior:

- **put validation.** a body that is not a JSON object, or that fails strict intake (duplicate keys, trailing data, type coercion), or whose path is not a safe single file name, is rejected with `400`. the id is not part of the body — it is the path — so there is no id to validate in it; the same safe-name rule gates every item endpoint, so a name the list publishes is one every `GET`, `PUT`, and `DELETE` can address. a body above a 32 MiB cap is `413`.
- **get of a stored file that no longer parses** (corrupted out of band) returns `500` with an error naming the id.
- **operational store failures.** a write, rename, or permission failure on the disk store is a server-side fault: it surfaces as `500` naming the failure, never as a `4xx` client error. the frontend's error line shows the decoded message either way, so a disk error is never mistaken for a bad request.
- **delete of a missing id** is `404`.

### frontend

a storage adapter sits behind one interface, and the app talks only to the interface:

```typescript
interface SessionStore {
  list(): Promise<SessionSummary[]>
  get(id: string): Promise<Conversation | null>
  save(id: string, doc: Conversation): Promise<void>
  remove(id: string): Promise<void>
}
```

`Conversation` is the document body: `title`, `messages`, `createdAt`, `updatedAt`, and the optional `usage` record. it has no `id` field — the id is the store's key, the file's name, and every store operation takes it explicitly. the in-memory and on-disk shapes are identical, so a round trip is byte-transparent: the bytes a `save` sends are the bytes a later `get` returns.

- **`diskSessionStore`** fetches against `/api/sessions*` and checks every response against the documented statuses — `200` for list, `200` for get (a `404` is the one case that resolves to `null`), `204` for the mutations. any other status rejects, carrying the backend's message — decoded from either of the two documented error shapes, a plain `error` string or the nested `error.message` object. a network failure rejects the same way. there is no warn-and-swallow path: a save that never reached disk surfaces as a failure, never as a success. every item URL is built as `/api/sessions/` + `encodeURIComponent(id)` — a safe filename is not necessarily a URL-safe string: `issue#1` is a legal conversation name, and the `#` in a URL built by string concatenation would truncate the request at the fragment separator, sending a different path and 404-ing the conversation into a ghost; the mux hands the handler the decoded segment, so `issue%231` arrives as `issue#1` and the store's id rule passes it unchanged.
- **`useSessions()`** is the mirror hook, shaped like the `useLocalStorage` hook the app already uses so the code around it is unchanged: it returns the working copy (`conversations`, the full estate), the update function (`setConversations`), a `loading` state, and the `error` and destructive-operation entry points. on mount it hydrates: a `list()`, then a `get()` for each listed id, assembled in the order the list returned them (updated descending, id ordinal-ascending). a `list` failure — the initial read failing outright — leaves the copy empty, the error line up, and `loading` true: the session gate stays closed over an estate the tab could not read, and the recovery is a reload after the backend recovers, never a mutation issued against an untrusted empty copy; a `get` that fails for one id drops that entry, names it in the error line, and loads the rest. `setConversations` is a ref-backed update function with today's call shape: at call time it derives the next working copy from the ref it holds, installs it into the ref and the React state, and enqueues the diff's `save`s to the store on the serial chain before returning — the mirror runs exactly once per call, at call time, never inside React's updater (react may invoke updaters more than once) and never in a later effect (which settles after the state it mirrors has logically moved, and could join the chain behind a logically earlier operation); added or changed conversations (reference inequality; the app's updates build new objects only where they changed) are `save`d to the store, and hydration seeds the ref and the state through the hook's internal non-mirroring path so a load issues no save. removals are not diffed: the destructive handler makes an explicit `remove(id)` call, because it awaits the settle to release its guard. every store mutation joins one serial chain in invocation order — the adapter's entire ordering machinery, a handful of lines: a `remove` issued after a save cannot execute ahead of it and re-create the file. the only reader is the initial hydration, and the session gate (below) is what keeps every mutation behind it, so no read-ordering machinery is needed. there is no coalescing: each mirrored commit is one PUT, and a long turn shows one PUT per commit — the mirror's honest behavior on a loopback appliance where a disk write is cheap. a failed operation records its decoded message in the single `error` slot, which the next successful store operation clears.
- **the app renders the error.** while the app's derived error is non-null the UI shows one quiet error line — a muted notice near the conversation input, no new chrome — so a failed operation, a write or a read that would otherwise leave the rail or a selection silently empty, is visible in the same moment it happens. the slot holds the most recently failed operation's message; it is cleared by any later successful store operation — the visible form of the `console.warn` the app has always used for the localStorage mirror. the same line also carries a failed `/api/config` fetch — which the config hook exposes rather than swallowing into an empty config: without it, an empty model list and the failing sends that follow would come with nothing on the page that says why, and the line that names the failure and points at restart-and-reload persists until reload, since the binary it accuses sits behind the page itself. when both are outstanding at once — the dead-backend case — the line is one and the ordering is fixed: the session error when present, otherwise the config error. a session failure therefore takes the line over the persistent config failure, and the config failure resurfaces the moment the session failure settles — a persistent failure can never mask a live one.

the conversation surface of `App.tsx` rewires from `useLocalStorage('pane:conversations')` to the hook — and only there. the find, the sync effect, the commit effect, and the handlers keep their shape:

- **selection is a find, not a fetch.** `activeConversation = conversations.find(c => c.id === activeId)`, exactly as today — over the hydrated working copy. when `activeId` changes, the sync effect loads the found conversation into the chat hook: `loadConversation` seeds messages from the conversation's own array reference and the usage record from its record (an omitted key ≡ `null`), so the meter's reading moves with the conversation and shows the same bands after a reload as before it — the revisit condition the usage arc named. there is no in-flight window on selection: state is local, the find is synchronous, and the previous conversation's state is replaced in the same effect that runs for the new selection — a layout effect (`useLayoutEffect`), not a passive one, so the replacement lands before paint: the first frame that shows the composer enabled already shows the loaded messages, the loaded meter reading, and the seeded snapshot, and a send pressed the instant the selection or the gate changes builds from that loaded history, never from the previous conversation's state. **the hydration-completion transition** is the one case where the find and the state move apart: the working copy starts empty and fills asynchronously, so the sync effect is a no-op while hydration is in flight (keyed on the selection and the loading flag, it runs once hydration settles — the working copy is fully installed, every listed document fetched — not when the list alone resolves). it then reconciles the retained selection against the installed copy: a match loads the document and seeds the commit snapshot from its own references, so a retained selection comes back with its full history on screen and a subsequent send builds from that real history instead of an empty one; no match — a retained `pane:activeConversation` id that names no stored conversation, the upgrade case — clears the selection (`activeId` set to null, chat state and meter reset), rather than followed: the chat view shows the empty state, no request is ever made for the ghost id, and a subsequent send takes the create branch instead of streaming work that could not be mirrored to any conversation.
- **the commit guard makes a read not a write.** the commit effect (on `chat.messages`, `chat.usageRecord`) gains one clause on top of the shape it has today: while chat's (messages, usage) are the same references a snapshot ref holds — seeded from the loaded conversation's own references, usage normalized (an omitted key ≡ `null`), at the moment the sync effect loads it, and advanced to the references the last commit mirrored — it issues no write. selecting or reloading a conversation is therefore identical to the state the store holds, and a mere open re-stamps neither the stored document's `updatedAt` nor the rail's ordering; any real change — a new message, a usage event, a thinking-collapse toggle — builds the document (messages replaced, usage from the record, title falling back to the first user message, `updatedAt` stamped) and `setConversations` mirrors it. both sides of the comparison normalize the optional `usage` field identically, so a document that omits the field reads as unchanged whether it arrived by fetch or by in-memory creation, and the guard holds for every document the conversation shape declares valid. the triggers are the same that write localStorage today; the write path is unchanged, the destination is the store.
- **the rail orders by last activity.** the conversation list renders in (updated descending, id ordinal-ascending) order — the same comparator the store's `List` applies, so screen order and disk order agree — and a commit that stamps `updatedAt` moves the conversation to the top of the rail in the same render.
- **destructive operations.** delete removes the conversation from the working copy — the handler calls the hook's `remove(id)`, which joins the serial chain — and, when deleting the active one, first aborts the in-flight turn and detaches the commit owner so a live stream cannot mirror a write after the deletion. the mirror is state-first, like the localStorage it replaces: the screen shows what state holds immediately, and if the `remove` fails the error line names it, the disk still holds the conversation, and a reload restores it from the store. while a delete of the active conversation is in flight, a small destructive-pending guard — reactive state plus a mirror ref, the same mechanism that closes the composer gate — keeps the send, retry, new-conversation, and selection entry points closed, so no turn the reader initiates in the window can stream work that will never be mirrored. selection is refused for a sharper reason than the others: the sync effect re-attaches commit ownership to whatever is selected, so a selection made during the window reopens the fence — any message mutation on the newly selected conversation (even a thinking-collapse toggle) then commits a save behind the in-flight delete, which re-creates the file after the deletion, with no error. a rail click dropped in the brief pending window is the price; the same click works once the window closes. there is no clear-all — settled by the operator in round-4 review triage (2026-08-19): bulk-wiping the stored sessions is a file operation on the data directory, the store's private property that nothing else writes to, so stopping pane and deleting the directory wipes the estate. the per-browser keys a pre-arc profile may still hold (`pane:activeConversation`, `pane:chatPreferences`, and the legacy `pane:conversations` / `pane:model` / `pane:systemPrompt`) are per-profile browser data that no product action touches: they leave the profile only when the user clears browser data, and the dormant pre-arc copy among them is inert to pane, which reads only the store.
- **the session gate.** every session-mutating entry point — both new-conversation controls, the send button (and the enter key), and the retry button — is closed while hydration is incomplete or while the destructive-pending guard is up. hydration is incomplete until the working copy is fully installed — the initial `list` **succeeded** and the `get` for every id it listed has settled (a failed `get` drops its entry but still settles the transition; a failed `list` settles nothing — `loading` stays true, the gate stays closed, and the error line names the failure, so no mutation can ever run over the untrusted empty copy, the recovery being a reload after the backend recovers) — one boundary, one meaning of the `loading` flag, no looser reading at which a mutation could slip in between the list and its documents. the controls render disabled, the handlers early-return, and the composer's gate sits before the input clear, so a send pressed into either window is refused rather than silently discarded and the typed text survives (the input stays editable in both cases). the gate is total because the mirror's read-before-mutation assumption depends on it: the only reader of the store is the initial hydration, and a mutation issued before it settles breaks the assumption invisibly — a new-conversation PUT that the settling snapshot then overwrites leaves a file on disk the rail never shows. the hydration half needs no mirror ref: `loading` moves only true→false, so a state read can never be stale in the dangerous direction, unlike the destructive guard, which moves both ways. and because the selection sync is a layout effect, the flip instant is safe to open on: the first painted frame after `loading` goes false already shows the active conversation's state, so the gate needs no second 'chat state is settled' condition — one flag, one boundary.
- **the meter reads state.** the toolbar receives the active conversation's usage record from the synced chat state — `activeConversation ? chat.usageRecord : null` — so during hydration (no working copy yet) and with no active conversation it reads `?`, and otherwise it always shows the record of the conversation on screen: chat state is the loaded record of the active conversation, seeded by the sync effect, and the sync effect's reset primitive (`loadConversation(null)`) drops the reading together with the messages when the selection goes away.

**what stays in the browser:** `pane:activeConversation` and `pane:chatPreferences`. these are per-browser view state — a second machine pointed at the same store should restore the sessions, not necessarily the last-open tab or the last-dialed model.

**no import.** pre-arc localStorage conversations are never imported into the store, and no product action touches them — clear-all is not in the design. that copy stays in the profile that created it — exportable as markdown from that profile — until the user clears browser data. nothing is imported, nothing is destroyed, no first-run prompt. the retained active-selection key is likewise a per-browser fact: on first load after the move, an id that names no hydrated conversation is not found by the selection's find, and the selection is cleared at the hydration-completion transition, not followed.

## seam census

the calls made in the design session, confirmed by the operator:

1. **storage ownership / protocol.** the backend owns storage. `/api/chat` keeps taking the full history on every request and the backend keeps no in-memory conversation state. the alternative — the backend loads history from the store and `/api/chat` takes an id — makes the backend stateful per session and buys nothing for a one-human, one-instance appliance.
2. **storage format.** one JSON file per conversation, opaque to the backend, the frontend's camelCase shape canonical end to end; the conversation's id is the file's name, not a field of the body. a single store file rewrites the whole estate on every change; SQLite violates the no-database principle.
3. **no import.** pre-arc localStorage data is never imported into the store. it stays in the browser; a reader who wants it on disk exports it as markdown first.
4. **disk only.** the store is always on: no mode config key, no localStorage conversation path, no UI surface for storage. the browser keeps per-browser view state only. settled by the operator in the 2026-08-19 review session, who ruled disk-only over the previously settled two-mode design.
5. **browser state stays local.** active-conversation selection and chat preferences remain per-browser localStorage state.
6. **data directory.** `data_dir` in config, default `~/.local/share/pane`, configurable — a leading `~` in the configured value expands to home. the operator confirmed the default and the configurability.
7. **projection case.** the list projection uses the body's camelCase content fields — the id comes from the filename, which carries no case question — rather than the snake_case the rest of pane's API speaks, on the ground that the projection is a subset of the opaque document and its name. agent-recommended in the design session; the operator responded by parking the casing question as its own arc (the `camelcase-snakecase` roadmap card, researching) — this arc keeps one case per resource, and wire-casing standardization is that card's territory.
8. **session gate.** while hydration is incomplete — including the case where the initial `list` fails outright, in which case it never completes and the gate stays closed until a reload after recovery — or a destructive operation is pending, the session-mutating entry points — new conversation, send (button and enter), and retry — are closed: the controls are disabled and the handlers refuse, while the composer's input remains editable and the send gate sits before the input clear, so typed text is never lost. the composer half was settled by the operator in round-2 review triage (2026-08-18), preferring it over disabling the whole composer; the total gate was settled in round 2 of the mirror-model review (2026-08-19), where the ungated new-conversation controls were found to race the initial hydration.
9. **the runtime mirror model.** React state is the working truth for the tab's lifetime; the disk store is its durable mirror — hydrated on load, persisted on change — the same runtime shape the app has today on localStorage. live cross-tab sync is traded for reload-scoped sync: a change in one tab is on disk, but another tab sees it only on reload. settled by the operator 2026-08-19 (mercurius session s_3YmSkWBJCyrT), which retired the store-as-source-of-truth machinery the earlier design carried — the operations queue, save coalescing, transition tokens, and the per-class failure ledger.
10. **rail tiebreak.** the rail's (updated descending) order breaks ties on the id ordinal-ascending — on disk in the store's `List` and on screen in the working copy's display order — so two conversations that share an `updatedAt` order identically in both places. the comparison is UTF-8 byte order on both sides: Go's string compare is byte order natively, and the frontend compares the id's `TextEncoder` bytes (never the raw-string operator, which orders by UTF-16 code units and diverges on supplementary-plane characters, and never a locale-sensitive comparison) — so the promised identical ordering does not depend on either side's collation luck, for any id that passes the store's id rule.

## scenarios

**s1 — the appliance.** a machine runs pane beside ollama. the browser profile dies, the user moves to a different browser — every conversation, tool-call history, thinking blocks, usage record, is present on first load: the record lives in the data directory on the machine, outside the browser. an OS reimage survives only insofar as the data directory survives: the default `~/.local/share/pane` sits in the user's home and is erased with the OS on a full reimage, so the reimage case requires `data_dir` pointed at preserved storage, or the directory restored afterward — a tarball of it is enough. this arc provides the mechanism the reimage case runs on; it does not provide the preservation itself (the deferred item below owns that). when it holds, the context meter shows the same bands after the reimage as before it.

**s2 — two tabs, reload-scoped.** two tabs of the same pane hold independent working copies of the same disk record. a change made in one tab is mirrored to disk immediately but is invisible to the other tab until that tab reloads — the operator settled this trade (2026-08-19): for a one-human appliance, last-write-wins plus reload-scoped freshness is the right cost line, and live sync would cost queue and conflict machinery the app did not have on localStorage. if both tabs edit the same conversation, the last write wins and the other tab's copy is stale until reload.

## what does not change

- the SSE protocol, the chat loop, tool calls, approvals, thinking display — untouched.
- the `/api/chat` request shape: full history, system-prompt mode. the backend remains a stateless proxy.
- `/api/config` — unchanged; the store has no setting to report.
- no auth, no settings UI, and no new chrome; the store's only setting is the optional `data_dir` location. the visible additions are the error line shown when a store operation fails — the most recent failure, cleared by the next successful store operation — or when the initial `/api/config` fetch fails (persists until reload; behind the session error when both are up) — and the session gate — new conversation, send, and retry disabled during hydration and the destructive-pending window. the composer's text is never lost by a gate.
- the usage meter: record placement, bands, and invalidation rules are unchanged. the record now round-trips through the store, and the display reads it from the synced chat state of the active conversation; it shows `?` during hydration and with no active conversation, so the screen never shows one conversation's reading under another's selection.

## accepted residuals

- **last-write-wins, reload-scoped sync.** within one tab, state is the working truth and the store is its mirror: the screen is always at least as fresh as the disk, and mutations reach the store in invocation order (the adapter's serial chain), so a delete issued after a save lands after it. across tabs there is no live sync — the operator settled the trade on 2026-08-19: each tab hydrates on load and owns its working copy; a change in one tab is on disk, but the other tab's copy is stale until reload. two writers to one conversation: the last PUT wins. the named path to tightening this is the server-assigned version mechanism in the deferred list.
- **the error line is one slot.** the hook records the most recent failed operation — a hydration `list`, a mirrored write, a `remove` — and clears it on the next successful store operation — for the initial `list`, which leaves the session gate closed, that next success is the reload after the backend recovers — the visible form of the `console.warn` the app has always used for the localStorage mirror. a failed save of one conversation can therefore be cleared by a later successful operation on another, and there is no per-conversation tracking: the divergence self-heals on the next write of the affected conversation, which in a chat client is the next message, and the backend logs the rejected operation. settled with the mirror model (2026-08-19), in place of the per-class failure ledger the store-as-source-of-truth design carried.
- **corruption is out of band.** the store validates on write, and on write only: a file damaged after the fact (disk error, manual edit) whose body is no longer a JSON object is skipped in the list with a warning and fails on get with an error naming the id, and there is no repair path. a file that is merely renamed or hand-edited is not corruption in this sense — the id is the name, so it is a conversation under its new name, or the same conversation with new content. a temp file orphaned by a process death mid-write is likewise inert: `List` reads only `*.json`, so it never appears in the rail or loads as a conversation; it stays on disk as the store's private debris, and the operator's directory deletion — the bulk-wipe path — is the cleanup that removes it.
- **the session endpoints have no auth.** the sessions sit behind whatever `listen` address is configured. binding to a non-loopback address exposes full conversation history to the network — that is the `authentication` card's territory (it scopes the mechanism to persistent sessions with a persistent installation), not this arc's.
- **unload and hard termination can lose a turn's tail.** closing the tab or reloading while the mirror's PUT for the latest commit is in flight discards whatever the reader has seen since the last completed write; a browser crash or power loss can do the same. the operator declined a beforeunload guard against this (2026-08-18) as over-hardening for a one-human appliance; the window is the drain of one PUT, and a reload after the turn settles restores the complete turn.
- **a failed destructive operation leaves commit ownership detached.** the delete-of-the-active-conversation path aborts the in-flight turn and detaches the commit owner before issuing the store operation, so a live stream cannot mirror a write after the deletion. when that awaited delete fails — a `500` from a broken disk store — the owner is not restored: the screen already shows the post-delete state (the state-first mirror) and a reload — which rehydrates from the store that still holds the conversation — is the recovery. on a loopback appliance an operational failure of a destructive op means every save is failing too — the error line is already up, and a reload is the natural recovery. the operator accepted this residual (2026-08-18) rather than building a restore branch that re-attaches the owner when a destructive op fails.
- **there is no clear-all.** bulk-wiping the stored sessions is the operator's file operation on the data directory, and per-browser profile state — retained selection, preferences, and any pre-arc `pane:conversations` copy — leaves the profile only when the user clears browser data. settled by the operator in round-4 review triage (2026-08-19), in preference to the clear protocol's confirm, guard, and recovery machinery.

## deferred (and why)

- **import from pre-arc localStorage.** the operator settled no import. a manual path — markdown export, then an import surface — is a feature to be asked for, not a repair this arc owes.
- **server-assigned session versioning.** the mechanism that would close the last-write-wins residual across clients: the store assigns each conversation a version it increments on every accepted save, the document carries it, a save compares the version the caller holds and rejects a stale one (409), and the error line becomes a conflict line the reader resolves — re-read or discard, while holding in-flight work. a client-side timestamp cannot do this job: a wall clock is not monotonic across tabs, so only a counter the store itself assigns is a true per-conversation order. the 2026-08-19 trade — reload-scoped sync — lowers this card's urgency: staleness until reload is the settled semantics, and the mechanism would add conflict *detection* on top of it. revisit when two tabs or machines editing the same conversation in real use makes a lost turn worth detecting. the roadmap card `server-assigned-session-versioning` holds the work.
- **retention / pruning.** the store grows without bound. a policy (age, count, size) is a separate call with separate numbers.
- **carrying the data directory between machines.** a tarball of the data directory is already portable; first-class sync or backup is a different arc with different stakes.
- **auth on the session endpoints.** the `authentication` card owns it — it scopes the mechanism to persistent sessions with a persistent installation, which is exactly this arc's new exposure.
- **search, pinning, folders across conversations.** rail ergonomics, not storage.
- **a non-JSON store format** (SQLite, single-file store). declined on the no-database principle; the format earns its way in if file counts ever stress the filesystem.
