## accepted browser save boundary

the accepted recovery policy needs a record of an interrupted request even when the browser receives no tool-dispatch event. today `useSessions` returns immediately after scheduling a save, catches failures inside its serial queue, and exposes no success acknowledgement. `App.tsx` mirrors chat state through a passive effect. the prototype instead syncs a file before tool dispatch. transplanting the latter would silently introduce a backend execution ledger, which was explicitly deferred.

before issuing a browser chat POST, save the user message and an in-progress turn marker through the existing session-store facade, and await that specific save's success. if it fails, send no chat request. on reload an unfinished marker means the prior request may have run tools; absence of received call events is not proof of non-execution. require explicit reconciliation before tool-enabled continuation. received outcomes still mirror incrementally without waiting for every write before executing the next tool.

the pre-send document is a private candidate, not an optimistic change to the conversation working copy or the passive mirror. keep the composer text until sending begins. a rejected save discards the candidate from local state and queued future snapshots; a later rename or unrelated save must not accidentally persist its user message or marker. acquire a same-tab preparation guard before building the candidate: block conversation switching, creation, deletion, reset, duplicate sends, and edits to the candidate's conversation until the save-and-send decision finishes. on success, install the acknowledged candidate and initiate the POST for its original owner before releasing that guard, with no intervening asynchronous step. on failure, release the guard, retain the draft, and show the save error; no POST occurs. this guard covers normal app actions, not browser closure, reload, or another browser. an unacknowledged write may have reached disk, and a crash between save and POST may still leave a conservative unfinished marker; neither case permits automatic sending or retry on reload.

this is a pre-send save barrier, not a dispatch acknowledgement protocol. `/api/chat` stays stateless and does not read or write conversation files. a terminal record supersedes the marker only after its normal save succeeds. a crash before that save may conservatively require reconciliation despite actual success. simultaneous edits from another browser retain the existing last-writer limitation; no session revisions or distributed ownership are added. document these limits rather than claiming exactly-once execution.

the guarantee is conservative recovery for the current browser/store workflow, not a global transaction across clients or remote tools. do not substitute a server-side execution journal or claim that a successful SSE write acknowledges browser persistence.

### adapter, message, and replay types

define a narrow interface equivalent to `Round(ctx, request, emit) -> final/error`. requests contain portable messages, tools, intent, and request-local continuation. connection/model/effort are immutable for the submitted turn; rotating credentials come from the shared manager. progressive events carry text, thinking, and tool previews; only a terminal validated round can yield executable calls. adapters never approve or execute tools.

#### terminal status and execution eligibility

successful normalized finishes are exactly `stop` and `tool_calls`. every abnormal round returns a classified error plus non-executable partial display data, never a successful final with salvageable calls. the matrix is an explicit pane acceptance policy; neither HTTP 200 nor a parseable call is sufficient.

| adapter | raw terminal evidence and validated output | normalized result | tools eligible |
|---|---|---|---|
| chat completions, including both qwen profiles | the single requested choice finishes with `stop`, has no calls, then receives `[DONE]` | `stop` | no |
| chat completions, including both qwen profiles | the choice finishes with `tool_calls`, has one or more fully validated calls, then receives `[DONE]` | `tool_calls` | yes, subject to shared-loop checks |
| chat completions | `length` or `content_filter`, even with complete-looking calls | `incomplete` error, preserving the safe raw reason | no |
| chat completions | missing/unknown finish, deprecated `function_call`, conflicting finishes, `stop` with calls, or `tool_calls` without calls | `protocol` error | no |
| subscription Responses | `response.completed` with explicit `response.status: 'completed'`, no response error/incomplete details, and a valid finalized item set without function calls | `stop` | no |
| subscription Responses | the same successful terminal evidence, with one or more fully validated finalized function-call items | `tool_calls` | yes, subject to shared-loop checks |
| subscription Responses | `response.incomplete` with status `incomplete`, including token limits or filtering | `incomplete` error | no |
| subscription Responses | `response.failed` with status `failed`, or an upstream `error` event | classified upstream/auth/allowance error | no |
| subscription Responses | missing/unknown status, queued/in-progress terminal status, event/status mismatch, contradictory error fields, or invalid/inconsistent item set | `protocol` error | no |
| either | local cancellation or explicit upstream cancelled status; stream/read failure; required terminal boundary missing at EOF | `cancelled`, `transport`, or `truncated` error respectively | no |

for chat completions, null finish fields before the terminal choice are normal. accept final empty-choices usage chunks between that finish and `[DONE]`; they do not replace the choice's finish. require one choice, stable call indices/ids, and no new content/call deltas after its finish. EOF before `[DONE]` is truncated even after `tool_calls`; `[DONE]` without a choice finish is a protocol error. this applies to generic legacy connections too: do not retain unsafe finish inference as a compatibility fallback.

for the subscription adapter, support `response.done` only as the explicitly recognized compatibility spelling of a terminal envelope, with the same required status/output validation and error mapping; do not infer success from its name. this spelling is handled by the inspected spike parser, not live-established by the sanitized fixture. the first fully decoded terminal envelope closes the round without waiting for EOF or `[DONE]`. item/argument `.done` events alone never close the round. event/status contradictions already observed before that boundary fail closed; do not keep reading indefinitely to look for a second terminal event.

assemble finalized subscription items in provider order from `response.output_item.done` and terminal-output backfill. terminal `output: []` does not erase completed streamed items: the sanitized live tool fixture has that shape. merge matching ids without duplication, permit completion of previously partial fields, and reject changes to already finalized call identities/arguments or conflicting completed items. every started item must finish or have a valid terminal backfill; do not salvage the valid calls from a partly invalid round. a supplied item status must be completed, and call ids, item bindings, names, and object-valued JSON arguments must validate. terminal success with no calls may contain ordinary answer or refusal text; refusal is not itself a tool authorization or a failed transport.

eligibility is not dispatch: the shared loop additionally requires the tool was offered, the round intent allows tools, approval is granted, and cancellation has not occurred. any call in a tools-withheld forced-final response makes that round non-executable. a later bad round does not undo tools from earlier rounds; retain those outcomes and apply the recovery policy, without automatic retry.

the public status vocabulary is documented in the [chat completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) and [Responses streaming reference](https://developers.openai.com/api/reference/resources/responses/streaming-events), checked 2026-09-24. subscription evidence remains the pinned spike report and `spike/openai-subscription/testdata/codex/live-shape-toolcall.sse`, not a claim that the public API documents every subscription-route behavior.

retain pane's existing public message/tool-call JSON shapes. the prototype's flattened call shape is not permission to migrate every browser document. add optional assistant `origin` and versioned `continuation` fields. origin records alias, effective/requested effort as available, and resolved identity. continuation contains a format/version, identity, ordered provider items, and explicit pane-call/provider-call/provider-item bindings. represent provider items as bounded opaque JSON interpreted only by the adapter, not as Responses-specific fields in the shared loop.

identity includes provider/protocol, upstream model, canonical service including meaningful endpoint path, profile, and subscription account scope. use a domain-separated non-secret account binding, not tokens or their fingerprints. the prototype's fixed-prefix hash is a pseudonymous identifier, not anonymous data; redact it from ordinary logs and fixtures. refresh and alias rename do not invalidate replay. preserve raw provider ids only inside their originating envelope; portable call ids remain pane-owned, stable, unique, and collision-safe when adapted to provider constraints.

#### subscription replay identity format

freeze the production subscription continuation format as `format: 'codex-responses-items'`, `v: 1`, with the following identity encoding. the envelope version also versions these identity rules; JSON property order and whitespace are not identity. compare decoded field values, never serialized JSON bytes. provider item ordering and encrypted payload bytes remain significant under their separate replay rules.

| identity field | canonical v1 value |
|---|---|
| `provider` | exact string `openai-codex` |
| `protocol` | exact string `responses` |
| `upstream_model` | exact resolved upstream model id sent on the request, case-sensitive; never the pane alias |
| `service` | exact string `https://chatgpt.com/backend-api/codex/responses`, including scheme and full generation path, no trailing slash, port suffix, query, or fragment |
| `profile` | omitted for this provider; an explicit empty string decodes to the same absent profile; any nonempty profile is invalid |
| `account_scope` | `chatgpt:` followed by 24 lowercase hexadecimal characters, computed as specified below |

the service value is a compile-time constant tied to the adapter's fixed destination, not reconstructed from browser metadata, a redirect, or a configurable URL. validate incoming subscription identity against that exact value; do not silently normalize an alternate spelling into compatibility. a destination/path change requires an explicit replay-compatibility decision. this full-path production value intentionally differs from the prototype's shorter service label; prototype conversations are not a production migration input.

account-scope algorithm v1: take the exact nonempty `chatgpt_account_id` string obtained by the credential manager; do not trim, case-fold, Unicode-normalize, or use token bytes. UTF-8 encode the concatenation of the literal ASCII domain `pane-account-scope-v1:` and that account id, with no NUL, newline, or separator beyond the domain's final colon. SHA-256 that byte string, take the first 12 digest bytes, encode them in lowercase hexadecimal, and prepend `chatgpt:`. this deliberately retains the prototype's established hash algorithm rather than inventing a random per-install salt. missing account identity fails before generation; never hash an empty id as a usable account scope. the fixed domain is versioned domain separation, not a secret salt, authentication proof, or anonymity guarantee.

synthetic golden vectors: `acct-pane-test-a` maps to `chatgpt:ea1e30f202148af5945f8c85`; `acct-pane-test-b` maps to `chatgpt:3847545a9761c55a4f3fe66b`. fixtures must use these or other explicitly synthetic ids, never real account values. raw account ids stay in the credential/authenticated-transport path, including the required provider account header; they do not enter browser state, saved conversation identity, or logs.

pin the constants, byte encoding, hash width/case, and identity comparison with production fixtures before freezing continuation tests. assert stable binding across token refresh, process reload, and alias changes; account/model/service changes must exclude replay while preserving stored data. reject malformed account scopes and unknown envelope versions without guessing a migration. future changes to service spelling, account domain/encoding, or field interpretation require a versioned compatibility/migration decision and fixtures; do not regenerate old bindings from current credentials or rewrite saved identity on load. qwen has no durable continuation envelope under this format and does not acquire durable replay from this identity definition.

#### continuation validation and limits

validate envelope shape/version, identity/origin agreement, allowed item types, ordered companions, text consistency, and one-to-one call bindings. incompatible envelopes stay stored but are excluded from the request. a compatible-looking but malformed envelope cannot inject another account's data, tools, destinations, or instructions. use portable fallback only when valid portable history can be constructed; otherwise fail before network activity. never fabricate a successful result for an orphaned call. input mutations and stale bindings must not replay a mismatched envelope.

empty reasoning summaries are valid: terminal encrypted items must survive regardless of display deltas. qwen reasoning is request-local only, attached to the actual assistant round rather than a fragile index that changes when a system message is inserted. no closed-turn reasoning echo. model switching converts the outgoing representation without rewriting stored history.

qwen's replayable reasoning stays exclusively in the Go loop's request-local continuation state. never serialize that state into `round_ready`, `round_complete`, an assistant continuation envelope, or `Conversation.turns`; qwen rounds emit no durable reasoning-replay envelope. the separate `thinking_delta` display path may still show and save visible thinking as today, but that display field is excluded from chat wire projections and is never a source for reconstructing request-local continuation. completion, cancellation, or failure ends the request-local lifetime; reload and new-turn recovery cannot restore it from saved display text.

use the existing 32 MiB store cap as the aggregate chat-body and aggregate decoded model-round budget as well; no new smaller per-envelope limit is introduced. an envelope cannot exceed its enclosing request/round budget. apply body limits before decoding, bounded SSE line/event buffers, and aggregate counters across events rather than only limiting individual events. count retained output/continuation payloads and tool results against the prospective conversation size in the browser; an over-cap save must remain an explicit persistence failure, never erase the last acknowledged marker or trigger retry. a received upstream round that exceeds its budget fails before tools execute. an oversized tool result occurs after execution and must be treated as an unpersisted outcome requiring recovery, not permission to repeat the call. preserve diagnostics without silently truncating encrypted items. the prototype's 512 KiB envelope limit is not carried over.

the browser's prospective document check measures the UTF-8 byte length of the exact serialized JSON body it will save, including metadata and JSON escaping: equivalent to `new TextEncoder().encode(JSON.stringify(candidateDocument)).byteLength` when that is the save serializer. do not use JavaScript string length or sum individual field lengths. the cap is `32 * 1024 * 1024` bytes; exactly the cap is allowed and anything larger is rejected. use the same serialization for checking and saving, and count the serialized chat request separately against its body cap because its recovery projection has a different shape.

add a non-ASCII boundary fixture containing multibyte text where JavaScript string length stays below the cap but serialized UTF-8 bytes exceed it. assert browser/store agreement for serialized bodies exactly at the cap and one byte over, including JSON syntax/escaping and metadata. an oversized pre-send candidate must preserve the draft and acknowledged document and issue no chat POST; an oversized post-execution outcome remains an explicit persistence failure, never permission to repeat the tool.

### pane events and recovery record

preserve current text/thinking/usage event meanings while adding an identified turn/round lifecycle. before tool approval or execution, publish the finalized assistant round, origin/envelope, and requested-call set as recovery state. retain individual outcomes immediately; `round_complete` promotes an already-known round idempotently rather than duplicating its messages. every event is bound to its request and round so late events cannot mutate a different conversation. finalize authoritative usage once per round; optional cached/reasoning counts may be preserved without changing the existing latest-alias usage behavior.

keep an optional versioned turn record in the opaque conversation document: turn id, selected identity, phase, finalized pending assistant rounds, per-call execution state/outcome, received partial display text, and interruption/reconciliation notes. old documents without it remain valid. partial answer/tool previews are not replayed as completed model output.

distinguish known not-dispatched, denied/rejected, dispatched, result received, and unknown outcome. emitting today's `tool_call_executing` before argument parsing is not evidence of dispatch. register approval before notifying the browser, validate arguments as objects, and recheck cancellation immediately before calling the executor. MCP transport failure after dispatch can mean unknown side effects; do not label it safely retryable merely because an error returned. stop on unknown execution state instead of automatically asking the model to repeat work.

make dispatch certainty explicit in `ToolExecutor`'s return contract, owned by `llm` and implemented by `mcp.Manager`: a result equivalent to `ToolExecution{Dispatch, Content, Duration, IsError, Err}`, where `Dispatch` is exactly 'not_dispatched', 'result_received', or 'unknown'. `Err` is diagnostic, not the dispatch discriminator. a missing/invalid outcome is a contract error handled conservatively as unknown, never the zero-value equivalent of non-execution. model adapters neither supply nor interpret this executor result.

the MCP boundary assigns 'not_dispatched' to local route/server/preflight failures and cancellation observed before invoking the client. a decoded, correlated tool reply is 'result_received', including `CallToolResult.IsError`; retain its actual error content instead of collapsing it into an ordinary Go error. a structured correlated protocol-error reply can also establish response receipt if the client exposes that fact. once the client call begins, timeout, cancellation, disconnect, nil/malformed reply, or an ordinary client error is 'unknown' unless structured transport evidence proves no dispatch or a correlated reply. do not infer certainty from error text, elapsed time, or the apparent kind of failure. 'result_received' means a reply arrived, not proof that the tool succeeded or made no side effects.

`tool_call_result.execution_state` carries the dispatch-evidence value 'not_dispatched', 'result_received', or 'unknown'. the shared loop separately maps that evidence to the call record: 'not_dispatched' means known non-execution; 'result_received' becomes 'completed' or 'failed' according to the returned result; 'unknown' becomes unknown and stops further dispatch and model rounds. denial, argument rejection, and approval timeout before the executor remain loop-owned non-execution, with their existing distinct reasons. an unknown outcome may emit its diagnostic and explicit state, but never an observed tool-result message or ordinary `round_complete`; only the later explicit recovery projection can add an attributed placeholder. preserve earlier received outcomes; the turn's execution summary is unknown if any call is unknown, otherwise known if any reply was received, otherwise none. a browser that misses these events still follows the conservative saved-marker policy.

retry-from-scratch is available only with affirmative evidence of no execution; after known work, continue as a new user turn from recorded results. a dropped SSE stream, malformed critical lifecycle event, or reload of an unfinished marker requires conservative uncertainty, including when no call was received. reconciliation records what the operator actually knows; an unknown result is never presented as a model-observed success. build truthful portable result notes only from that record, and never dispatch a historical call during reconstruction.

new-turn continuation carries answers/results but not the prior qwen loop's ephemeral reasoning. deliberate repetition is a separate explicit action. disable model selection during the active turn, including approvals; model switching after interruption is allowed only through the same recovery rules, not as a way around them.

### serialized lifecycle contract

the new browser sends a fresh opaque `turn_id` in `/api/chat`, allocated before the save barrier, and a required `recovery: {v: 1, turns: TurnRecord[]}` alongside `messages`. `recovery.turns` projects every prior turn record retained in the submitted conversation, including interrupted turns with no received rounds; it excludes the fresh turn's pre-send marker, which remains in the saved document. an empty array explicitly means no prior records. recovery is pane-only input, never forwarded to a provider as an extra request field. the backend validates ids and never uses them as paths, credential selectors, or authority to execute historical tools. messages retain the current JSON shape with optional `turn_id`, `round_id`, `origin`, and `continuation`; newly generated messages identify their turn, and round ids combine that identity with a local ordinal. use a portable id mapping rather than exposing provider ids as pane call ids.

for this new request contract, the submitted `messages` array must contain exactly one message whose `turn_id` equals the request's `turn_id`: it must be the final array element and have `role: 'user'`. the fresh message has no round id, tool calls/result binding, assistant origin/continuation, or recovery-placeholder metadata. no prior recovery record may use the fresh id. this is the sole exception to the prior-record rule: all messages tagged with any other turn id must bind to a supplied prior record. the original user message and reconciliation notes may share their prior turn's id; uniqueness here applies only to the fresh id, not to all message turn-id references. validate these rules before system-message normalization or opening SSE; violations return `invalid_recovery` without a provider request. legacy requests omitting both top-level fields retain the separately stated legacy behavior.

the browser allocates the fresh id once, uses it on the new user message and saved pre-send marker, and sends that same id after acknowledgement; do not regenerate it between saving and POST. the saved marker's `user_message_index` identifies that final user message. subsequent lifecycle events and generated rounds belong to this id. the marker is omitted only from the outgoing prior-record array, not from the acknowledged conversation. a later submission allocates a new id and includes the now-prior record under the normal history rules.

persist `Conversation.turns?: TurnRecord[]`. a v1 record has `id`, `v`, `model_alias`, `user_message_index`, `state` ('in_progress', 'completed', 'interrupted'), `last_seq`, `rounds`, optional `origin`, `partial_text`, `error_code`, `terminal`, and `reconciliation`. `terminal` retains the observed `turn_end` outcome/execution pair; missing terminal evidence is not inferred from an empty call list. each round record has `round_id`, a pending finalized `assistant` until normal promotion, `message_index` once represented in history, `calls`, and `committed`. normal round promotion sets `committed: true` and removes the duplicate pending assistant but retains call outcomes; recovery projection can instead set `message_index` with `committed: false` and retain assistant evidence as specified below. each call has the existing portable call shape, `state` ('pending', 'denied', 'rejected', 'not_dispatched', 'dispatched', 'completed', 'failed', 'unknown'), optional recorded result, and optional reconciliation. recovery-only changes are document changes even when messages/usage retain the same references.

the request projection reuses these records, omitting only display-only `partial_text` and UI decorations; it does not omit inconvenient unresolved turns. all message indices in the projection refer to the submitted `messages` array before backend system-prompt normalization, not to positions after adapter conversion. `user_message_index` must identify a user message with the same `turn_id`; promoted rounds must identify an assistant message with matching turn/round ids, calls, and origin/continuation. call ids bind one-to-one to the corresponding portable tool result messages. recompute indices after recovery projection, preserve ids, and reject duplicate record/round/call identities, dangling references, contradictory recorded results, or a record for the fresh turn. the prior-record requirement applies to message turn ids other than the submitted fresh id; the single final fresh user message follows the exception above. legacy messages without these ids remain portable history and acquire no invented recovery evidence.

operator reconciliation is structured, not a boolean: a turn's `reconciliation` contains `execution` ('none', 'known', 'unknown'), a nonempty operator-attributed `note`, and `message_index` pointing to that exact note in a user-role history message tagged with the prior turn id. ambiguous calls also retain their own reconciliation with `execution` and `note`; those notes must appear in the turn's bound history note and, where applicable, the attributed suffix of a recovery placeholder defined below. 'unknown' means the operator explicitly chose to proceed with uncertainty, not that pane observed a result. preserve original states and returned results; reconciliation annotates them rather than overwriting them. operator observations must not masquerade as model-observed or MCP-returned success. missing whole-round data is covered by the turn-level note without inventing call ids.

critical lifecycle events add `turn_id` and monotonically increasing `seq`; round/call events also identify `round_id` and the canonical call id. keep visual deltas separate from the authoritative record. the browser ignores duplicates, rejects gaps in critical sequence as loss of recovery information, and rejects mismatched ownership. a malformed critical event terminates consumption conservatively rather than being skipped.

| event | authoritative content and ordering |
|---|---|
| `turn_start` (new) | resolved origin and selected alias; after request validation, before first upstream generation |
| `round_ready` (new) | finalized assistant, origin and optional durable envelope, normalized finish, pending call set; before any approval or dispatch; excludes qwen request-local reasoning |
| `tool_call_approve` | pending approval; register before sending the event; not proof of dispatch |
| `tool_call_executing` | validated call is about to dispatch; emitted after approval and cancellation checks; conservatively unknown if no outcome follows |

| `round_complete` | existing assistant/tool-message payload plus round identity; idempotent promotion after all calls are terminal and known |
| `turn_end` (new) | `outcome` ('completed', 'failed', 'cancelled'), `execution` ('none', 'known', 'unknown'), optional error/partial display text; authoritative terminal record |
| `done` | compatibility stream terminator after `turn_end`; alone does not prove safe recovery |

the shared loop produces lifecycle state; the API maps it to SSE. keep error messages displayable through the existing `error` event, but only `turn_end` makes a terminal recovery claim. on transport/write failure, stop further dispatch and let the browser's saved marker express uncertainty. after cancellation or unknown MCP outcome, do not emit a normal `round_complete` with invented results. successful non-tool responses also pass through `round_ready`/`round_complete` so continuation is stored without reliance on thinking deltas.

before a new turn after interruption, use the normative portable recovery projection below. known returned failures remain results, not non-execution. the UI offers retry only on affirmative no-dispatch evidence, otherwise asks for outcome confirmation. an operator may explicitly acknowledge an outcome remains unknown and choose to proceed; preserve that uncertainty and require an explicit action, never silently mark the operation successful. the pending-marker save includes the projected messages and reconciliation changes before the next POST. none of this reconstruction calls an executor.

backend intake validates the recovery projection before opening SSE or contacting a provider, without reading the session store. reject malformed/version-unknown projections and orphaned or mismatched messages with a typed `invalid_recovery` error. reject any prior `in_progress` record, interrupted record without either trustworthy terminal non-execution evidence or explicit bound reconciliation, and unresolved 'pending', 'dispatched', or 'unknown' call with a typed `recovery_required` error. a terminal `execution: 'none'` can establish non-dispatch for pending calls only when no recorded call outcome contradicts it. completed records require successful terminal evidence and only terminal known call outcomes; no label alone overrides contradictory state. after reload, the browser classifies an abandoned marker as interrupted, preserving the missing terminal evidence, before offering reconciliation.

a reconciled interrupted record is admissible for a new turn once all known results and operator-attributed notes are represented consistently in history. explicit 'unknown' reconciliation is admissible only as acknowledged uncertainty, never as evidence for retry-from-scratch. the browser continues to offer that retry only on affirmative non-execution evidence; the backend rejects unresolved recovery regardless of which UI action initiated the request. terminal known work requires continuation from its recorded results, not dropping the prior turn from the request. validate the same projection on both browser and backend, with the new marker save including the reconciliation first. reconstruction and validation never call an executor.

#### portable recovery projection

for each retained finalized assistant round, preserve its content and complete ordered `tool_calls` array. immediately follow that assistant message with exactly one `role: 'tool'` message per call, in call order, sharing the round/turn ids and the matching `tool_call_id`. do not insert a user note inside this batch. after all batches for the interrupted turn, append its bound operator reconciliation note as a `role: 'user'` message, then the new user message. keep already projected rounds/results exactly once by round/call id; repeated serialization, save, or reload must not append duplicates. if there is no finalized round, append only the reconciliation note, never promote partial call previews into history.

an actual received result is stored on the call as `result: {content: string, is_error: boolean}`. tool-message `content` must equal that received content exactly; an empty received string is still a result. success/failure remains in the call's original 'completed'/'failed' state and `is_error`, since portable tool messages have no universal success-status field. every synthetic tool-role message instead has pane-only `recovery_placeholder` metadata, with one of the kinds below. this metadata persists and participates in intake validation but is removed by provider conversion; the explicit attribution in `content` remains visible to the model. never store placeholder content in `call.result`, emit it as an observed MCP outcome, change the original call state, or mark an interrupted turn completed because its history is now syntactically paired.

| recorded evidence for the call | portable tool-message content | `recovery_placeholder` |
|---|---|---|
| 'completed' or 'failed' with received result | exact `result.content`, including returned failure text | absent |
| 'denied', 'rejected', or 'not_dispatched'; or pending call covered by consistent terminal `execution: 'none'` | `pane recovery: this call was not executed.` | `not_executed` |
| ambiguous call explicitly reconciled as `execution: 'none'` | the same non-execution sentence, followed by the operator suffix below | `not_executed` |
| 'pending', 'dispatched', or 'unknown' with explicit `execution: 'unknown'` reconciliation | `pane recovery: execution outcome unknown; no result was received.` followed by the operator suffix | `unknown` |
| ambiguous call reconciled as `execution: 'known'`, but no actual tool reply was received | `pane recovery: no tool result was received; the outcome below is operator-reported.` followed by the operator suffix | `operator_reported` |
| ambiguous call without applicable terminal evidence or explicit reconciliation; received-result state without its result | no projection; block the new request | not applicable |

the exact operator suffix is `\noperator note: ` followed by that call's recorded reconciliation note. known local non-execution needs no invented operator observation; retain its denial/rejection diagnostic in the record. operator reports never replace actual received results or override contradictory evidence of execution. the turn-level note starts `operator reconciliation: ` and incorporates each call note verbatim, associated with its call id; its entire content equals `turn.reconciliation.note`. when affirmative terminal non-execution permits retry without outcome reconciliation, no operator reconciliation message is required: use the known-non-execution row and preserve the terminal evidence. an ordinary new-turn continuation after recorded work follows the explicit reconciliation path.

these tool-role placeholders are provider scaffolding to close historical call/result pairs, not observed results. chat-completions conversion keeps their role, call binding, and content; Responses conversion uses the normal `function_call_output` shape with the same content and mapped call id. neither adapter invents a placeholder, infers execution from its role, nor dispatches a historical call. backend intake validates the placeholder kind and exact generated text against the supplied call/terminal/reconciliation evidence; it rejects placeholders passed off as received results, missing/extra tool messages, reordered batches, and notes inserted inside batches. finalized assistant continuation can be reused only under the existing binding checks; recovery does not manufacture an opaque provider result or revive qwen's expired request-local reasoning.
